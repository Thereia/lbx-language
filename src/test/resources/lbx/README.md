# LBX 黑盒测试集

作业提交内容第 3 项。**一条命令跑完全部测试**（在仓库根目录执行）：

```
mvn -o -q test
```

`mvn test` 跑两种测试：`src/test/java/lbx/` 下的单元与端到端测试，以及本目录下 55 个黑盒用例
（由 `BlackBoxSuiteTest` 调用 `TestRunner` 接入）。也可以不经 Maven 单独跑黑盒这一部分：

```
mvn -o -q compile
java -cp target\classes lbx.TestRunner
```

退出码：0 表示全部通过，1 表示有失败。输出会逐个列出用例，并在最后给汇总与失败清单。

## 一、为什么叫「黑盒」

`TestRunner` **不调用解释器的任何内部 API**，每个用例都是新起一个 JVM 跑 `lbx.Main`，只观察三样东西：

| 观察对象 | 断言 |
|---|---|
| 子进程 stdout | 与同名 `.expected` 文件**逐字节**一致 |
| 子进程 stderr | 错误用例与同名 `.expected` 文件逐字节一致 |
| 退出码 | 正常用例 0、错误用例 1、命令行用例 2（语法文档 §10.2） |

所以测试集只依赖「源码进、输出出」这个外部行为，解释器内部随便怎么重构都不会让测试失效。

## 二、目录约定

| 文件 | 含义 |
|---|---|
| `cases/名字.lbx` | 正常用例的 LBX 源码 |
| `cases/名字.expected` | 期望的 stdout（逐字节比对，末尾换行也算） |
| `cases/名字.in` | 可选：喂给子进程的标准输入（当前只有 `12-io` 用到） |
| `errors/名字.lbx` | 错误用例的 LBX 源码 |
| `errors/名字.expected` | 期望的 stderr（整行，含 `[LBX 词法/语法/运行时 错误]` 前缀） |

约定：所有文件都是 **UTF-8 无 BOM、行尾 LF**。解释器自己也只输出 LF
（`Interp` 里 `print` 故意不用 `println`，因为 `println` 在 Windows 上会输出 `\r\n`，
按字节比对的测试跨平台就不一致了）。运行器仍会把两侧的 CRLF 归一成 LF，属于防御性处理。

## 四、期望输出是手写的，不是跑出来的

`.expected` 文件全部按**语法文档 §8 的打印规则手写**，然后才跑解释器验证。
这一点很重要：如果拿解释器的输出反过来当期望，解释器的 bug 会被一起固化进测试集，测试就永远全绿而没有意义。

第一轮跑下来恰好抓住了**两处我写错的期望值**（`len("ab") + f(1)` 是 4 不是 5；
文件末尾有无换行会影响「文件意外结束」报错到哪一列），也验证了实现本身的正确性。

## 五、加一个用例的方法

1. 在 `cases/`（或 `errors/`）下新建 `名字.lbx`；
2. 按语法文档手写 `名字.expected`；
3. 需要标准输入就加 `名字.in`；
4. 重跑 `java -cp target\classes lbx.TestRunner`。
