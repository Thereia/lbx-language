## 1. 先建立心智模型：解释器只做三件事

编译器课程里你已经写过其中两件：

| 步骤 | 输入 → 输出 | 你在实验里写过 | 本项目对应 |
|---|---|---|---|
| ① 词法分析 | 字符流 → 记号流 | `lexer.c`（状态机 + 配对缓冲区） | `Lexer.java` |
| ② 语法分析 | 记号流 → 语法树 | `rd41.c`（递归下降、消除左递归） | `Parser.java` + `Node.java` |
| ③ 求值 | 语法树 → 结果 | **没写过，这是新的一步** | `Interp.java` |

关键区别：`rd41.c` 走完文法只会打印「接受 / 拒绝」——它**认识了**句子但没**算**它。解释器在第 ② 步不是判对错，而是**把结构建成一棵树**，然后在第 ③ 步**再走一遍这棵树，把每个节点算成一个值**。

```
脚本文件(.lbx)
   │  整个文件一次读成 String（不需要配对缓冲区，见 §3.6）
   ▼
Lexer.lex()  ──►  List<Token>        每个记号带 行:列，供报错定位
   │
   ▼
Parser.parseProgram()  ──►  Node（语法树根，kind = BLOCK）
   │
   ▼
Interp.run()  ──►  结果写到 stdout；出错抛 LbxError → Main 打到 stderr 并按退出码退出
```

回答「解释器和编译器有什么区别」就用这张图：**编译器**在第 ③ 步之前会生成另一种语言的可执行产物（`gcc lexer.c` → `lexer.exe`）；**解释器**没有产物，`java -cp build lbx.Main` 这个程序自己就是运行环境，直接算结果。

## 2. 一个例子走完全程：`print(1 + 2 * 3);`

### 2.1 词法分析（真实运行输出）

`examples/demo-tokens.lbx` 的全部内容就是一行 `print("hi");`：

```
> java -cp build lbx.Main --tokens examples/demo-tokens.lbx
  1:1   IDENT    print
  1:6   OP       (
  1:7   STR      "hi"   hi
  1:11  OP       )
  1:12  OP       ;
  2:1   EOF
```

要点：

- 每个记号都带 **行:列**，这就是后面 `[LBX 语法错误] 行 2, 列 1: ...` 里行列号的来源。
- `print` 是 `IDENT` 而不是关键字——它只是全局作用域里的一个**内置函数变量**（见 §3.8）。
- `STR` 记号的 `value` 是**未解码的原文** `hi`（这里恰好没有转义），转义与 `${}` 插值留给 Parser 处理（原因见 §3.6）。

### 2.2 语法分析（真实运行输出）

`examples/demo-ast.lbx` 的内容：

```lbx
// demo-ast.lbx —— 讲解演示用：配合 `--ast` 看语法树形状（docs/07-实现讲解.md §2.2）
if x == 1
    print("a" + str(2 * 3));
end
```

```
> java -cp build lbx.Main --ast examples/demo-ast.lbx
BLOCK
  IF
    BIN (==)
      VAR (x)
      INT = VInt[v=1]
    BLOCK
      EXPR
        CALL
          VAR (print)
          BIN (+)
            STR = VStr[v=a]
            CALL
              VAR (str)
              BIN (*)
                INT = VInt[v=2]
                INT = VInt[v=3]
```

要点：

- 树的形状证明了优先级正确：`+` 的两个孩子中，右边是 `*` 的子树，所以 `1 + 2 * 3` 不会被算成 `(1+2)*3`。
- `if` 节点只有两个孩子（条件、真分支），没有 `else` 时就没有第三个孩子——`Interp.exec` 用 `kids.size() > 2` 判断。
- 语句块也是节点（`BLOCK`），所以 `exec` 是统一递归的，不需要为「块」单独写一套逻辑。

### 2.3 求值

```
Interp.run()
 ├─ 第一遍遍历顶层语句：遇到 FUNC 就登记成 VFunc、遇到 TYPE 就登记字段默认值   ← 「定义即注册」
 ├─ 注册 9 个内置函数到全局作用域
 └─ 第二遍遍历顶层语句：逐条 exec
      exec(EXPR) → eval(CALL) → 求值 callee 得到内置函数 print，再求值各实参
        eval(BIN +) → Interp.binOp → Ops.add(int, int)  ← §5 的类型规则只在这里
      print 拿到 [VInt(7)]，按 §8 规则输出 "7\n"
```

## 3. 逐文件讲解

### 3.1 Token.java（17 行）—— 词法分析的输出格式

**为什么需要**：如果没有统一的记号类型，Parser 拿到的就是一堆字符串，判断「这是关键字还是变量名」要用字符串比较散落各处。把记号定成一个不可变对象（`record`）+ 一个 6 值的枚举，Parser 里就只剩 `kind` 与 `text` 两个概念。

**内容**：

- `enum TokenKind { INT, STR, IDENT, KEYWORD, OP, EOF }`
  —— 关键字与运算符都归 `KEYWORD` / `OP`，具体是哪个靠 `text` 区分。这样枚举只有 6 个值，而不是给 `if`、`while`、`+`、`==` 各开一个枚举常量（40 个）。
- `record Token(TokenKind kind, String text, Object value, int line, int col)`
  —— `value` 只在 `INT`（存 `Long`）和 `STR`（存原文 `String`）上非空。
- `String describe()`
  —— 产出错误消息里的说法：普通记号是 `'end'`（带引号），`EOF` 是「文件结尾」。语法文档 §10.3 规定的「期望 ';'，实际遇到 'end'」就是它拼出来的。

**可能被问**：「为什么关键字不用单独的枚举？」——因为关键字的集合在语法文档 §3.2 里是一张表，用表 + `text` 判断比 17 个枚举常量更容易与文档对照，而且新增关键字只改词法表一行。

### 3.2 LbxError.java（38 行）—— 三类错误统一成一种异常

**为什么需要**：词法、语法、运行时三类错误都要按 §10.3 的格式打到 stderr 并以退出码 1 结束。如果让 Lexer / Parser / Interp 各自 `System.err.println`，格式和退出码一定会漂移，黑盒测试就没法断言了。

**内容**：

- 三个静态工厂：`lex(line, col, msg)`、`syntax(line, col, msg)`、`runtime(line, msg)`
  —— 词法与语法错误**必须**给列号，运行时错误只给行号（`col = 0`），这直接对应 §10.3 的两种格式。
- `format()` 拼出 `[LBX 语法错误] 行 7, 列 15: 期望 ';'，实际遇到 'end'`。
- 构造函数里 `super(msg, null, false, false)` 关掉栈追踪：错误只在 `Main` 顶层打印一次，建栈是白花的。

**可能被问**：「为什么不用多个异常类？」——三类错误的差别只有前缀和是否带列号，用一个类加一个 `phase` 字段就够；分成三个类反而要在 `Main` 里写三个 `catch`。

### 3.3 Node.java（53 行）—— 整棵语法树只有一个类

**为什么需要**：语法树是词法、语法、求值三层之间唯一的「数据契约」。如果做成 `Expr` 10 个子类 + `Stmt` 10 个子类 + `Visitor` 接口，光样板代码就要多写约 500 行，而我们要做的事一模一样。

**内容**：

- `enum Kind`，共 24 个值，分三组：字面量（`INT/BOOL/NULL/STR/INTERP`）、表达式（`VAR/BIN/UN/CALL/INDEX/FIELD/ARRAY/STRUCT`）、语句与声明（`BLOCK/EXPR/ASSIGN/IF/WHILE/FOR/RETURN/BREAK/CONTINUE/FUNC/TYPE/FIELD_DEF`）。
- `final Kind kind` + `final int line`（不可变），`text` / `value` / `kids` / `names` 四个可变字段。
- 文件头注释里**逐条**写明了每种 kind 用哪几个字段，例如：
  - `BIN`：`text` 是运算符，`kids = [左, 右]`
  - `FOR`：`names = [循环变量]`，`kids = [被遍历表达式, 循环体]`
  - `INTERP`：`kids` 是**交替出现**的「字面量段」与「表达式节点」

**可能被问**：「一个类装所有节点，会不会容易写错？」——会，所以配了 `enum Kind`：`kind` 写错编译就过不去（如果用字符串就不会报错）。另外 `Parser` 里所有造节点都走 `lit()` / `unary()` / `block()` 几个小工厂方法，字段赋值只有那几处。

### 3.4 Value.java（154 行）—— 基本数据类型在这里

**为什么需要**：作业第 1 条要求「整数，字符串等基本数据类型」。如果用 `java.lang.Object` 装所有值，这句话在代码里就不存在了，而且 `typeof()`、§5 运算规则、§8 打印规则会各自散落在求值器里。

**内容**：`sealed interface Value permits VInt, VStr, VBool, VNull, VArray, VStruct, VFunc, VBuiltin`，三个方法：

- `String typeName()` —— 返回 `"int"` / `"string"` / `"bool"` / `"null"` / `"array"` / `"struct"` / `"function"`，即语法文档 §4 的类型表，也是 `typeof(x)` 的返回值。
- `String str()` —— §8 的「容器外层」形式：字符串**不加引号**。
- `default String repr()` —— §8 的「容器内层」形式：字符串**加双引号并转义**。

三个方法的分工用一个例子就说明白：

```lbx
print("abc");          // abc      ← 外层用 str()
print(["abc", 1]);     // ["abc", 1]  ← VArray.str() 内部对元素用 repr()
```

八个实现：

| 类型 | 实现 | 语义关键点 |
|---|---|---|
| 整数 | `record VInt(long v)` | 唯一数值类型，`/` 是整除（v1.0 无浮点） |
| 字符串 | `record VStr(String v)` | 不可变；`escape()` 供 repr 转义 |
| 布尔 | `record VBool(boolean v)` | 条件必须是它，没有隐式真值 |
| 空 | `record VNull()` + `NIL` 单例 | 全语言只有一个 null |
| 数组 | `final class VArray` | **引用语义**；`str()` 用 `Collectors.joining(", ", "[", "]")` |
| 结构 | `final class VStruct` | **引用语义**；字段用 `LinkedHashMap` **保序**，保序即 §8 的打印顺序 |
| 用户函数 | `final class VFunc` | 名字 / 形参 / 函数体 |
| 内置函数 | `final class VBuiltin` | 持一个 `Native` 函数接口，所以 9 个内置函数不用写 9 个类 |

**可能被问**：「为什么用 `sealed`？」——限制只有这 8 个类型，将来若 `eval` 里漏了某种类型，编译器/评审都能立刻看出来；同时它表达「LBX 的类型系统就是这 8 个」这个事实。

**可能被问**：「数组和结构为什么是引用语义？」——这是语法文档 §4 的明确规定：赋值与传参共享同一份。所以 `push(nums, 100)` 之后原数组就变了（`examples/features.lbx` 演示了这点）。

### 3.5 Ops.java（105 行）—— §5 运算规则集中一处

**为什么需要**：§5 是一张有明确规则的优先级表（`+` 支持 int 与 string、`/` 是整除且除零报错、比较只允许 int/string、逻辑运算要求 bool）。这些判断如果散落在求值器的每个分支里，改一条规则要翻五个地方。

**内容**（方法 ← 规则）：

| 方法 | 对应 §5 哪一条 |
|---|---|
| `add` | `int+int` → int；`string+string` → 拼接；混合类型报错 |
| `sub` / `mul` / `div` / `mod` | 只接受 int；`div` 检查除零、`mod` 检查模零 |
| `neg` | 一元负号，只接受 int |
| `eq` | `==`：类型不同直接 false（不报错）；数组/结构/函数比**引用** |
| `cmp` | `< <= > >=`：int 比数值、string 比字典序，其他类型报错 |
| `cond` | 条件必须是 bool（`if 1` 报「条件必须是布尔值，实际是 int」） |
| `not` | `not` 复用 `cond` 做检查 |
| `intOf` | 内置函数取整数参数的统一检查 |

**可能被问**：「`int + string` 为什么报错而不是隐式转换？」——§2 特色第 4 条：严格类型运算，不做隐式转换。这也让测试的期望输出没有歧义。

### 3.6 Lexer.java（255 行）—— 字符流 → 记号流

**为什么需要**：把「一串字符」变成「有类别的记号」，并且**在这一层就把行列号算准**——后面所有错误定位都依赖它。

**字段**：`src`（整个脚本）、`pos`（当前下标）、`line` / `col`（1 起算）、`out`（结果表）。

**方法逐个说**：

- `lex()` 主循环 —— 每次看当前字符决定走哪条路：空白跳过、`//` 行注释、`/*` 块注释、数字、标识符、字符串、运算符。**换行不产生记号**（v1.0 用 `;` 分句），但 `next()` 里会维护行号列号。
- `number()` —— 连续数字 → `Long.parseLong`，溢出报「整数超出范围」。
- `ident()` —— 连续字母数字下划线，然后**查关键字表** `KEYWORDS`：命中就是 `KEYWORD`，否则 `IDENT`。这就是「最长匹配 + 关键字优先」，所以 `iffy` 是一个标识符而不是 `if` + `fy`（和你词法实验里的处理一致）。
- `string()` —— 字符串字面量的**边界切分**。这里只切边界、**不解码转义**，值保留双引号之间的原文，原因有两条：
  1. `\${`（不想插值的美元号）与 `${`（要插值）必须在解码前区分开；
  2. 转义解码与插值拆段都属于「语义」，放 Parser 更集中。
  进入 `${` 后要**维护括号深度并整段跳过片段里的嵌套字符串**，否则 `${"内层字符串"}` 里的引号会被误认成外层字符串的结束引号（见 §5 的 bug 1）。
- `blockComment()` —— 找 `*/`，到文件尾还没找到就报「未闭合的块注释」，报的是**注释起点**的行列。
- `operator()` —— 运算符的最长匹配：先试 `== != <= >=`，再试 `&& || !`（归一化成 `and` / `or` / `not`），最后单字符表 `+-*/%<>=()[]{},;.`；都不匹配就报「非法字符 '@'」。
- `cur()` / `peek(k)` / `next()` —— 字符流小工具。`next()` 是唯一推进位置的地方，行号列号在这里统一维护，所以注释里、字符串里的换行也不会算错行。
- `isIdentStart` / `isIdentPart` —— 标识符字符集。

**可能被问**：「为什么不用词法实验里的配对缓冲区？」——那套缓冲区解决的是「流式读入 + 最长匹配回退」。我们一次把整个脚本读进 `String`，回退就是下标减一，脚本规模也不需要流式处理。这是 README §6.2 记录的一条设计决定。

**可能被问**：「v1.0 的字符串可以跨行，不会把错误吃掉吗？」——会，这是规格明确允许的（§3.3「可跨行」）。代价是漏写结尾引号时，报错位置在字符串**起点**而不是行尾。真出问题时能靠「未闭合的字符串」这条消息定位。

### 3.7 Parser.java（578 行）—— 记号流 → 语法树

**为什么需要**：把线性的记号流还原成「谁套着谁」的结构，并在这里做**静态检查**（分号、赋值目标、`return` 位置）；这些错误按规格属于**语法错误**，不该拖到运行时。

**两条路线**（这是本文件最重要的设计）：

- **语句：递归下降**——每个语句形式一个方法（`statement` / `ifStmt` / `whileStmt` / `forStmt` / `funcDecl` / `typeDecl`）。和你 `rd41.c` 是同一套做法。
- **表达式：优先级爬升**——§5 的九级优先级压成**一张表** `BIN` 加**一个方法** `expr(minPrec)`，替代 9 个 `or_expr` / `and_expr` / … 方法：

  ```java
  Node expr(int minPrec) {
      Node left = prefixOperand();
      while (true) {
          Integer p = BIN.get(peek().text());
          if (p == null || p < minPrec) break;
          next();
          Node right = expr(p + 1);      // +1 实现左结合
          ...
      }
  }
  ```

  和你做过的**预测分析表**是同一个味道：把「写 9 个函数」变成「查一张表」。

- 两个前缀运算符的优先级不是同一级，所以 `prefixOperand()` 里各自指定：`PREC_NEG = 8`（比 `*` 紧，所以 `-a * b` 是 `(-a) * b`）、`PREC_NOT = 3`（比 `==` 松，所以 `not a == b` 是 `not (a == b)`）。这两条都是 §5 表里写死的。

**方法逐个说**：

- `parseProgram()` —— 最外层循环，遇到 `EOF` 停；产出根节点 `BLOCK`。
- `topStatement()` —— **只在这里**允许 `func` / `type`（§12 文法里它们属于 `top_stmt`）。所以在函数里再写 `func` 会报「func 定义只能出现在最外层」。
- `funcDecl()` —— 名字、形参表、函数体；解析函数体前把 `funcDepth` 加一，结束后减一。
- `typeDecl()` —— `type 名 = { 字段 = 默认值, ... };`，字段顺序就是 `LinkedHashMap` 的插入顺序，也是 §8 的打印顺序。
- `statement()` —— 语句分发。除了上面几种，还负责：
  - `return` / `break` / `continue`：用 `funcDepth` / `loopDepth` 两个计数器判断位置是否合法，不合法**在语法阶段**就报错（§6.1）；
  - 单独一个 `;` 是空语句（返回一个空的 `BLOCK`）；
  - `表达式 (= 表达式)? ;`：如果看到 `=`，检查左边是不是 `VAR` / `INDEX` / `FIELD`，否则报「赋值号左边必须是变量、下标或字段」。
- `ifStmt()` —— `if` / `elif` / `else`，`elif` 用**嵌套 IF** 表示（`alt = block(List.of(ifStmt()))`）。注意这里有个坑：`elif` 分支递归调用自己时，那一层已经消费了结尾的 `end`，所以**这条路径上不能再要求一个 `end`**（见 §5 的 bug 2）。
- `whileStmt()` / `forStmt()` —— 循环体解析前 `loopDepth++`，这样循环里的 `if` 里写 `break` 也合法。
- `blockBody()` —— 语句序列，遇到 `end` / `else` / `elif` **停但不消费**（消费交给调用方），遇到 `EOF` 报「文件意外结束，缺少 'end'」。
- `postfix()` —— 后缀三兄弟：调用 `()`、下标 `[]`、字段 `.`，可任意串联（`a[2][1]`、`p.x`、`f(1)(2)` 都能解析）。都允许尾逗号。
- `primary()` —— 字面量、变量、`( 表达式 )`、数组字面量 `[...]`、结构字面量 `类型名 { ... }`。都不匹配就报「期望表达式，实际遇到 X」。
- `stringNode()` + `matchBrace()` + `parseFragment()` —— **`${}` 插值的实现**：
  1. 原文里没有 `${` 就直接 `decode()` 成一个 `STR` 节点；
  2. 有 `${` 就拆成「字面量段」与「表达式段」交替的 `INTERP` 节点；
  3. 每段表达式**当成一个独立小程序**重新走一遍 `Lexer` + `Parser`（`parseFragment`），并要求片段里只有一个表达式；
  4. `matchBrace()` 负责找出配对的 `}`，它会跳过片段里的字符串与嵌套的 `{}`——所以 `${len("a}b")}` 也能正确工作。
- 工具方法们 —— `peek` / `next` / `isOp` / `expectOp` / `expectKeyword` / `semicolon` / `expectIdent`。所有「期望 X，实际遇到 Y」的错误都从这几个方法出，所以错误消息格式天然统一。

**可能被问**：「为什么 `return` 的位置检查放在语法阶段？」——语法文档 §6.1 明确写的是「否则报语法错误」；而且这类错误不需要运行到那一行就能发现，早报早好。

### 3.8 Interp.java（453 行）—— 走树算值

**为什么需要**：前两层只是把程序翻译成结构，这一层才**执行**它。

**字段**：

- `List<Map<String, Value>> scopes` —— **作用域栈**，第 0 个是全局作用域，每次函数调用压一层。
- `Map<String, LinkedHashMap<String, Value>> types` —— `type` 声明的字段默认值。
- `PrintStream out` / `BufferedReader in` —— 输出与输入（由 `Main` 注入，UTF-8）。
- `int callDepth` —— 递归深度，上限 `MAX_CALL_DEPTH = 1000`（§7.1）。
- 三个内部异常 `ReturnEx` / `BreakEx` / `ContinueEx`。

**方法逐个说**：

- `run(program)` —— 分**两遍**：
  1. 第一遍遍历顶层语句，把 `FUNC` 登记成 `VFunc`、把 `TYPE` 登记进 `types`。这就是 §7.1 的「**定义即注册**」，它让函数可以互相递归、可以先调用后定义；
  2. 注册 9 个内置函数；
  3. 第二遍遍历顶层语句，逐条 `exec`。
- `exec(node)` —— 语句分发（`switch`）：`BLOCK` 递归执行；`EXPR` 求值后丢弃；`ASSIGN` 走 `assign`；`IF` / `WHILE` / `FOR` 是控制流；`RETURN` / `BREAK` / `CONTINUE` **抛出对应异常**往外跳；`FUNC` / `TYPE` 在第一遍已处理，执行阶段什么都不做。
  - 循环里 `catch (BreakEx)` 就是 `break` 的实现，`catch (ContinueEx)` 就是 `continue`。用异常的好处：不必让每个语句方法都返回一个「是否要中断」的标志位，深层嵌套里也能一跳到底。
- `assign(node)` —— 三种目标：变量（`assignName`）、下标（查边界后 `items.set`）、字段（查字段存在后 `fields.put`）。
- `eval(node)` —— 表达式分发：
  - `INT/BOOL/NULL/STR` 直接取 `value`；
  - `INTERP` 逐段拼接：**字面量段用 `str()` 直接取文本**，表达式段 `eval` 后取 `str()`；
  - `VAR` 走 `lookup`；
  - `BIN` 走 `binOp`，`UN` 走 `Ops.neg` / `Ops.not`；
  - `CALL` 走 `call`；`INDEX` / `FIELD` 做类型与存在性检查；`ARRAY` 构造 `VArray`；
  - `STRUCT` 先取类型默认值再覆盖字面量里给出的字段，字段不存在就报错。
- `binOp(node)` —— 先单独处理 `and` / `or`（**必须短路**：左边定了就不求值右边），其余运算符把两边算出来后交给 `Ops`。
- `call(node)` / `callFunc(func, args, line)` —— 实参个数与形参个数必须相等；压一层新作用域绑定形参；执行函数体；`catch (ReturnEx)` 拿到返回值；`finally` 保证无论正常结束、`return` 还是报错都弹出作用域并把 `callDepth` 减回去。走到 `end` 就是返回 `null`。
- `lookup(name, line)` / `assignName(name, v)` —— **§7.2 与 §7.3 的全部实现**，一共十几行：
  - `lookup`：从栈顶往下找，找不到报「未定义的变量 x」；
  - `assignName`：从栈顶往下找，**找到就改最近的那一个**（所以函数内能直接改全局变量），**找不到才在当前（最内层）作用域新建**。
- `indexOf(v, line)` / `outOfRange(...)` —— 下标必须是 `VInt`，越界报「数组下标越界：5（长度 2）」。
- `registerBuiltins()` —— 9 个内置函数用 **lambda** 直接塞进全局作用域的一张表，所以不需要为每个函数写一个类：
  - `print`：各参数用 `str()` 转换后以单个空格连接，末尾换行（§8）；
  - `input`：有提示就先输出提示并 `flush`，`readLine()` 返回 `null` 表示 EOF，此时返回 `VNull`；
  - `len`：数组取元素个数，字符串取**字符个数**（`codePointCount`，所以中文按字算）；
  - `int` / `str` / `typeof` / `push` / `pop` / `range`（`range` 有 1~3 个参数三种形式，步长不能为 0）。
- `expectArgs(name, args, n, line)` —— 内置函数参数个数的统一检查。

**两个实现上限（验收要主动说明）**：

1. 递归深度 1000 —— 规格 §7.1 规定，超出报「递归过深」而不是让 JVM 栈溢出崩溃；
2. `range` 生成的序列不超过 1000 万元素 —— 规格没写，是防止误写 `range(1000000000)` 把演示卡死的保护。

### 3.9 Main.java（94 行）—— 入口

**为什么需要**：解析命令行、把文件读成 UTF-8 字符串、把三类错误统一成退出码。它是**唯一**允许调用 `System.exit` 和打印错误的地方。

**内容**：

- 强制 UTF-8：`new PrintStream(new FileOutputStream(FileDescriptor.out), true, StandardCharsets.UTF_8)`。Windows 下 Java 默认字符集是 GBK，不这么做中文输出会乱码——和词法实验里 `SetConsoleOutputCP(65001)` 是同一类问题。
- 参数解析：`--tokens` / `--ast` 是两个自测与讲解开关，其余参数必须恰好是一个脚本路径。
- 退出码（§10.2）：正常 0；`catch (LbxError)` → 打印 `e.format()`、退出 1；参数错或文件读不到 → 退出 2。
- `tokenLine(t)` / `printAst(n, out, depth)` —— 两个开关的输出格式，缩进树就是这里递归打的。

## 4. 三个贯穿全局的设计

### 4.1 值模型：类型判断只有一处

`Value` 的 8 个实现 + `Ops` 的运算符方法，构成了「类型系统」的全部。任何地方要判断类型，只有两种写法：`instanceof`（在 `Ops` / `Interp` 内部）或调用 `typeName()`（对外）。这带来一个直接好处：**语法文档 §5 的规则表和 §8 的打印表，各自能被指到唯一一处代码**。

### 4.2 作用域：一个栈 + 两条规则

```
scopes: [ 全局 ]                     ← 栈底
        [ 全局, f 的参数作用域 ]      ← 调用 f 时压入
        [ 全局, f 的参数作用域, g 的 ] ← f 里调用 g
```

- 查找：从栈顶往下，找不到就报错（§7.2）；
- 赋值：从栈顶往下，找到就改**最近**的，找不到就在**栈顶**新建（§7.3）；
- 循环与 `if` **不压栈**（§7.2），所以循环变量在循环结束后还在，且函数内改全局变量会真的改掉——这两点都是规格写明的。

### 4.3 控制流：三个异常

`return` / `break` / `continue` 在深层嵌套里要「一跳到底」，所以用异常而不是标志位。三个异常都写 `super(null, null, false, false)` **关掉栈追踪**：它们被频繁抛出（循环里每轮都可能抛），建栈会明显拖慢性能。这也是性能测试那一步要提前知道的一点。

## 5. 实现中发现并修掉的两个真 bug

### bug 1：`${}` 插值里写字符串字面量

- **现象**：`print("${"内层字符串"}")` 报 `[LBX 词法错误] 行 1, 列 25: 非法字符 '内'`。
- **根因**：`Lexer.string()` 只知道「遇到未转义的 `"` 就结束字符串」，不知道 `${` 之后是**表达式**。于是内层字符串的引号被当成了外层字符串的结束引号，剩下的 `内层字符串"}...)` 就变成了散装字符。
- **修法**：`string()` 进入 `${` 后维护**括号深度**，深度大于 0 时把嵌套字符串整段收进来（含转义），深度回到 0 才继续按普通字符串处理。
- **连带发现**：测试里写的 `${typeof(p)}` 暴露了第二处问题——v1.0 把 `type` 同时定成「声明结构类型的关键字」和「取类型名的内置函数」，**同名导致 `type(x)` 永远无法调用**。修法是内置函数改名 **`typeof`**（只动内置函数表一行，不动文法），语法文档升 **v1.1** 并在 §13 第 10 条记录原因。

### bug 2：`elif` 链吃掉外层的 `end`

- **现象**：`examples/guess.lbx` 里 `judge` 函数用了 `elif`，紧随其后的 `func main` 报「func 定义只能出现在最外层」——但 `main` 明明在最外层。
- **根因**：`ifStmt()` 解析到 `elif` 时递归调用自己，**内层那一层已经消费了整条 `if` 链的结尾 `end`**；返回外层后，外层又执行了一次 `expectKeyword("end")`，把**函数的 `end`** 抢走了。于是 `judge` 的函数体一直没结束，`func main` 就被当成嵌套定义。
- **修法**：`elif` 分支自己造好 `IF` 节点后**直接 return**，不再要求第二个 `end`。
- **为什么值得写进 PPT**：这个 bug 只在「`if` 链 + `elif` + 函数」三者同时出现时才暴露，`features.lbx`（只有 `if/else`）测不出来。它是**跑真实示例脚本**才抓到的，说明「每步都用真实程序验收」比只测语法点更有效。

## 6. 验收问答准备

| 可能的提问 | 怎么答（指到哪） |
|---|---|
| 解释器和编译器区别？ | 不生成中间产物，`Interp` 直接走语法树算值；`gcc` 会把 C 变成 exe，我们不会 |
| 你的语言的基本数据类型怎么实现的？ | `Value.java`：sealed 接口 + 8 个实现，`typeName()` 就是文档 §4 的类型表 |
| 为什么不用 `Object` 装值？ | 那样「基本数据类型」在代码里不存在，`typeof()`、运算规则、打印规则会散落各处且靠 `instanceof` 重复判断 |
| 词法分析为什么要配对缓冲区？你有没有？ | 没有。缓冲区是为流式读入 + 回退设计的；我们一次读入整个脚本，回退就是下标减一 |
| 怎么保证 `iffy` 不被切成 `if` + `fy`？ | `ident()` 先最长匹配出完整标识符，再查关键字表（同词法实验） |
| 运算符优先级怎么实现的？ | 一张 `BIN` 表 + `expr(minPrec)` 优先级爬升；一元 `not` 与一元 `-` 各自指定优先级 |
| 为什么 `not a == b` 是 `not (a==b)`？ | 表格里 `not` 的优先级 3 低于 `==` 的 4（§5） |
| 作用域怎么实现的？ | `scopes` 栈 + `lookup` / `assignName` 两个方法，规则在 §7.3 |
| 函数内能改全局变量吗？ | 能：`assignName` 从栈顶往下找到就改最近的；找不到才在当前层新建 |
| `return` 怎么从深层嵌套跳出来？ | `ReturnEx` 异常，`callFunc` 里 `catch` 拿到返回值；`finally` 保证弹作用域 |
| 为什么异常要关栈追踪？ | 控制流异常抛得频繁，建栈开销大；错误异常只在顶层打印一次，也用不上栈 |
| 错误行列号怎么来的？ | `Lexer.next()` 统一维护 line/col → 存进 `Token` → `LbxError.format()` 拼 §10.3 的格式 |
| 语法错误和运行时错误怎么区分？ | 语法错误带行列、在 `Parser` 抛出；运行时错误只有行号、在 `Interp` / `Ops` 抛出 |
| 递归写太深会怎样？ | 计数到 1000 报「递归过深」退出码 1，不会让 JVM 栈溢出崩掉 |
| 为什么文档改过版本？ | 实现了才发现 `type` 关键字与内置函数同名，改内置函数名为 `typeof` 并记录决策；**改规格 + 记录，而不是让代码绕过规格** |
| 打印格式为什么这么定？ | 因为 M7 的黑盒测试要逐字节比对 stdout，所以 §8 把容器内外、引号、空格全写死了 |
| 支持闭包 / 类 / 浮点吗？ | v1.0 明确不支持（决策记录第 2、3 条与 §7.1），规矩是「语法自由但语义要够、不追求功能堆叠」 |
