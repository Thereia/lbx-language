# LBX 解释器性能测试报告

> 交付物对应：作业提交内容第 4 项「对 ZS 语言的性能测试报告」。
> 对应里程碑 M8。测试脚本在 `bench/`，运行命令见第 7 节。

---

## 1. 测试目的

用 **LBX 语言**编写性能测试脚本，与**功能完全相同的 Python 脚本**比较运行时间，回答两个问题：

1. LBX 解释器比 CPython 慢多少？（给出可复现的数字）
2. **慢在哪里？**（这是本报告的重点——只说"树遍历解释器慢"没有信息量，要指出是哪些操作在付出代价）

本报告不追求"LBX 比 Python 快"。一个几百行的教学用解释器比 CPython 快才是反常的；有价值的是量化差距并定位原因。

## 2. 测试环境

| 项目 | 值 |
|---|---|
| CPU | AMD Ryzen 9 7940HX |
| 内存 | 15.2 GB |
| 操作系统 | Windows |
| 解释器实现语言 | Java 17.0.12（HotSpot，默认 JIT） |
| 对照语言 | CPython 3.13.11 |
| 编译方式 | `mvn -o -q compile` |

## 3. 测试方法

1. **同一算法、同一输入**：每个基准都有 `.lbx` 与 `.py` 两个版本，算法逐行对应，输入数据都由代码生成、
   不依赖随机数（`bench/sort` 用倒序数组），因此两边算出的结果必须完全相同——这是比较有效性的前提。
2. **冷启动计时**：每次测量都新起进程（`java -cp target\classes lbx.Main ...` / `python ...`），
   包含各自运行时的启动开销，符合"用户运行一个脚本"的真实感受。
3. **重复取最小值**：每个组合跑 3 次取最小值，减少系统抖动影响（原始 3 次数据都记录在表里）。
4. **单独测启动开销**：另测"JVM 启动 + 空脚本"与"CPython 启动 + 空程序"，用于把启动开销从结果里剥离出来。
5. **正确性校验**：两边输出必须一致，否则数据作废。实测三组基准两边输出完全相同。

## 4. 三个基准

| 基准 | 脚本 | 工作量 | 考察点 |
|---|---|---|---|
| 1 | `bench/fib.lbx` / `bench/fib.py` | 递归 `fib(30)` | 函数定义、调用、参数绑定、作用域、递归返回 |
| 2 | `bench/loop.lbx` / `bench/loop.py` | `while` 累加 3000 万次 | 循环、整数算术、变量读写 |
| 3 | `bench/sort.lbx` / `bench/sort.py` | 冒泡排序 4000 个整数（约 800 万次比较交换） | 数组创建、下标读写、条件分支 |

三个基准覆盖了解释器最热的三条路径：**函数调用 / 循环算术 / 容器下标**。

## 5. 测试结果

### 5.1 原始耗时（含各自运行时启动开销，单位：秒，3 次取最小）

| 基准 | LBX | Python | LBX / Python | LBX 三次原始值 | Python 三次原始值 |
|---|---|---|---|---|---|
| 递归 fib(30) | **0.844** | **0.095** | **8.9 倍** | 0.856 / 0.844 / 0.844 | 0.095 / 0.101 / 0.105 |
| 循环累加 3×10⁷ | **2.652** | **2.433** | **1.09 倍** | 2.711 / 2.652 / 2.680 | 2.433 / 2.487 / 2.507 |
| 冒泡排序 4000 | **2.146** | **0.931** | **2.30 倍** | 2.212 / 2.146 / 2.176 | 0.931 / 1.113 / 0.954 |

（三组基准两边输出完全一致：`832040`、`449999985000000`、`1 4000`。）

### 5.2 启动开销（5 次取最小）

| 项目 | 耗时 |
|---|---|
| JVM 启动 + 空脚本 | 0.088 s |
| CPython 启动 + 空程序 | 0.014 s |

### 5.3 扣除启动开销后的纯计算耗时

| 基准 | LBX | Python | LBX / Python |
|---|---|---|---|
| 递归 fib(30) | 0.756 | 0.081 | **9.3 倍** |
| 循环累加 3×10⁷ | 2.564 | 2.419 | **1.06 倍** |
| 冒泡排序 4000 | 2.058 | 0.917 | **2.24 倍** |

## 6. 结果分析

### 6.1 最有意思的一条：纯循环上几乎打平（1.06 倍）

很多人以为"语法树遍历解释器一定比字节码解释器慢一个数量级"，数据不支持这个说法。原因是：

1. **JIT 把解释器的分发循环编译成了机器码**。`Interp.eval` 里那个 `switch (node.kind)` 被 HotSpot 编译后，
   每次分发只是几次间接跳转；而 CPython 的字节码 dispatch 是 C 层的一个大循环，本身也不是"零成本"。
2. **每一轮循环的工作量都很小**：`total = total + i` 在 LBX 里是「查两次变量 + 加一次 + 存一次」，
   作用域栈此时只有 1～2 层，`java.util.HashMap` 的查找被 JIT 优化得很充分。
3. 也就是说：**慢不慢不取决于"是树还是字节码"，而取决于每次操作背后真正干了什么。**

### 6.2 函数调用是最大短板（9.3 倍）

`fib(30)` 约 270 万次调用，LBX 每次调用要比 Python 多做：

| LBX 每次调用的额外动作 | 代价 |
|---|---|
| `new HashMap<>()` 建一层新作用域 | 对象分配 + 哈希表扩容，270 万次 |
| 形参逐个 `put` 进 HashMap | 每次调用 N 次哈希写入 |
| 实参装箱成 `VInt` / `VStr` 对象 | 每次调用 N 次分配（基本类型被包装） |
| 用 `ReturnEx` 异常做返回 | 抛异常本身有成本（已关栈追踪，但仍比直接返回贵） |
| `finally` 里弹作用域 + 递归深度计数 | 每次调用两次小操作 |

Python 的函数帧是 C 层分配的对象，且小整数有缓存，因此这条路径上差距被放大到近 10 倍。
**结论：函数调用密集的程序是 LBX 最不擅长的场景。**

### 6.3 数组下标是中等短板（2.24 倍）

`sort` 的内层循环每轮要做 4 次下标读写。LBX 每次下标操作要走：

```
eval(INDEX) → eval(数组表达式) → eval(下标表达式)
            → instanceof VArray 检查 → indexOf() 里 instanceof VInt + 拆箱
            → 越界检查 → List.get()
```

而 Python 的 `a[j]` 在 C 层一步完成（外加一次 `int` 对象拆箱）。再加上每次取出的值都要重新装箱成 `VInt`，
2.24 倍的差距符合预期。

### 6.4 为什么不是"几十倍"

如果用 `java.lang.Object` 到处装值、用字符串比较来判断运算符（很多教学解释器的写法），差距会大得多。
本项目能压到 1～9 倍区间，主要靠三点：

1. **`switch (node.kind)` 单点分发**，`enum` 的 switch 被编译成跳转表，而非字符串比较；
2. **类型判断是 `instanceof` + `record` 访问器**，不是 `getClass().getName()` 字符串比较；
3. **运算符规则集中在 `Ops` 静态方法**，JIT 能内联这些小方法。

## 7. 可验证的优化方向（本版本未实施）

按"预期收益 / 改动量"排序，均可在现有架构上增量实施：

| # | 优化 | 预期收益 | 改动量 |
|---|---|---|---|
| 1 | 局部变量改用**数组槽位**（先做一遍变量名到下标的解析），替代每次 `HashMap` 查找 | 对 fib 与 loop 都有明显收益，是收益最大的一条 | 中（要加一趟变量解析） |
| 2 | **小整数缓存**（-128～127 复用 `VInt` 实例） | 减少装箱分配，对 loop / sort 有帮助 | 小（`VInt.of()` 工厂） |
| 3 | `binOp` 里先做 `VInt` 快速路径再走通用 `Ops` | 对 loop / sort 有帮助 | 小 |
| 4 | 作用域用 `ArrayList` + 名字下标代替 `HashMap` | 与第 1 条合并实施 | 中 |

之所以**没有实施**：本作业的评分项是"性能测试"（10 分）而非"性能优化"，先把测量与归因做扎实、
并把解释器的正确性（55 个黑盒用例）守住更重要。上述方向已记录，若后续有时间可按 2 → 3 → 1 的顺序做。

## 8. 复现命令

在仓库根目录执行（先编译）：

```bat
mvn -o -q compile

:: 基准 1
java -cp target\classes lbx.Main bench\fib.lbx
python bench\fib.py

:: 基准 2
java -cp target\classes lbx.Main bench\loop.lbx
python bench\loop.py

:: 基准 3
java -cp target\classes lbx.Main bench\sort.lbx
python bench\sort.py
```

计时（PowerShell，每次新起进程，跑 3 次取最小）：

```powershell
$sw = [System.Diagnostics.Stopwatch]::new()
1..3 | ForEach-Object { $sw.Restart(); java -cp target\classes lbx.Main bench/fib.lbx *> $null; $sw.Stop(); $sw.Elapsed.TotalSeconds }
1..3 | ForEach-Object { $sw.Restart(); python bench/fib.py *> $null; $sw.Stop(); $sw.Elapsed.TotalSeconds }
```

把所有基准一次跑完并校对两边结果是否一致，见 `bench/README.md`。
