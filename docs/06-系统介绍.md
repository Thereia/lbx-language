## 第 3 页 —— 语言定位：三个词各管一件事

**页面**：三个维度

- **解释型**（怎么执行）：源码 → 记号 → 语法树 → 直接求值，**不生成任何中间产物**
- **通用**（能表达多少）：有状态、有条件、有无界循环 ⇒ 图灵完备，能写任意程序
- **脚本语言**（用来干什么）：动态类型 + 内置 I/O + 写好就能跑

**讲稿**：
> 作业要求里"解释型的通用脚本语言"这七个字，其实是三个独立的要求，我按三个维度理解：第一，解释型说的是执行方式——我的实现是读源码、切成记号、建语法树、然后遍历这棵树求值，全程不生成任何中间文件，所以跑完程序磁盘上不会多出可执行文件；第二，通用说的是表达力——语言有可变状态、有条件分支、有无界的 while 循环，这三样齐备就是图灵完备，能写任意程序；第三，脚本语言说的是用途与用法——动态类型、内置输入输出、不用编译，写好一个 `.lbx` 文件就能直接运行。后面几页我按这三个维度分别给证据。

## 第 4 页 —— 语言长什么样

**页面**：一段代表性代码（`samples/examples/features.lbx` 节选）+ 它的真实输出

```lbx
type Point = { x = 0, y = 0 };

func fib(n)
    if n < 2
        return n;
    end
    return fib(n - 1) + fib(n - 2);
end

p = Point { x = 3 };
nums = [1, 2, 3];
total = 0;
for n in nums
    total = total + n;
end
print("total = ${total}, p.y = ${p.y}, fib(10) = ${fib(10)}");
```

```
total = 6, p.y = 0, fib(10) = 55
```

**讲稿**：
> 这是语言的基本样子。语句用分号结束，代码块用 `end` 收尾——这是有意选的：用 `end` 就不需要处理花括号和结构字面量的歧义，也不需要维护缩进栈；用强制分号则让换行彻底变成空白，词法分析器不必产生换行记号，语法分析器也不必处理"表达式里的换行算不算结束"。这段代码同时演示了结构类型带字段默认值、数组、for 遍历、函数递归和 `${}` 字符串插值。顺便说一句，`p.y` 输出 0，是因为结构类型声明的默认值生效了。

## 第 5 页 —— 解释器怎么工作

**页面**：一张四段图 + 两条真实命令的输出

```
源码(.lbx) ──Lexer.lex()──► 记号流 ──Parser.parseProgram()──► 语法树 ──Interp.run()──► 结果
```

```
$ java -cp target\classes lbx.Main --tokens samples/examples/demo-tokens.lbx
  1:1   IDENT    print
  1:7   STR      "hi"   hi
  1:12  OP       ;
$ java -cp target\classes lbx.Main --ast samples/examples/demo-ast.lbx
BLOCK / IF / BIN (==) / VAR (x) / INT = VInt[v=1] / BLOCK / EXPR / CALL ...
```

**讲稿**：
> 解释器分三步，前两步和我之前做过的词法分析、递归下降分析实验是同一套技术。第一步词法分析把字符流切成记号流，每个记号带行列号——这也是错误消息里行列号的来源；第二步语法分析把记号流还原成语法树，语句部分用递归下降，表达式部分用优先级爬升：把九级优先级压成一张表加一个方法，而不是写九个 `or_expr`、`and_expr` 这样的方法；第三步求值器遍历语法树算结果。为了能看清楚前两步，我留了两个调试开关：`--tokens` 打印记号流，`--ast` 打印语法树，这两条命令的输出就是屏幕上这两段。

## 第 6 页 —— 四个关键实现决定

**页面**：四条，每条一行

1. **值模型显式化**：`sealed interface Value` + 9 个实现（int / float / string / bool / null / array / struct / function）
2. **语法树只有一个类**：`enum Kind` + 单个 `Node`，求值时一个 `switch` 分发
3. **表达式用优先级爬升**：一张优先级表 + 一个 `expr(minPrec)` 方法
4. **控制流用异常**：`ReturnEx` / `BreakEx` / `ContinueEx`，关闭栈追踪

**讲稿**：
> 有四个决定最影响这个项目的形态。第一，值模型是显式的：所有数据类型都是 sealed 接口的九个实现之一，而不是用 `Object` 装一切——这样"基本数据类型"在代码里看得见，`typeof()`、运算规则、打印规则各自只需要在一处实现。第二，整棵语法树只有一个 `Node` 类，用 `enum Kind` 区分节点类型，比"表达式十个子类加语句十个子类再加 Visitor"少写大约五百行样板。第三，表达式用优先级爬升，九级优先级压成一张表和一处递归。第四，`return`、`break`、`continue` 用异常实现，这样深层嵌套里也能一跳到底，不必让每个语句方法都返回"是否要中断"的标志位。这四个决定后来都收到了回报——加浮点类型时只动了四个文件，既有的五十五个测试用例一个都没改。

## 第 8 页 —— 测试：三层结构，一条命令

**页面**：

- **白盒（单元 + 端到端）**：`LexerTest` / `OpsTest` / `InterpTest`
- **蜕变测试**：`MetamorphicTest`——不写死期望值，只查不变式
- **黑盒**：60 个用例（18 正常 + 40 错误 + 2 命令行），每个用例新起一个 JVM，只看 stdout / stderr / 退出码
- 一条命令：`mvn -o -q test` → 37 个 JUnit 测试 + 60 个黑盒用例

**讲稿**：
> 测试分三层。最底层是白盒：直接调用解释器内部 API 的单元测试和端到端测试。中间一层是蜕变测试：它不写死期望值，只检查"同一件事的两种写法必须一致""排序结果必须非递减、元素不增不减、再排一次不变"这类不变式。最上面是黑盒测试集：六十个用例，每个用例都是一段用 LBX 写的程序加一个期望输出文件，运行器给每个用例新起一个 JVM 跑解释器，只观察三件事——标准输出是否与期望文件逐字节一致、标准错误是否符合约定、退出码是否正确。之所以要做成黑盒，是因为语言的对外契约就是"源码进、输出出"，这样解释器内部怎么重构都不会让测试失效。

## 第 9 页 —— 测试的有效性：怎么知道测试本身是可信的

**页面**：三个实证

1. 期望输出**照规格手写**，不是拿解释器输出粘回去 → 第一轮手写就抓出我自己算错的两处期望值
2. **故意注入故障验证守卫**：把行尾改回 `println`（Windows 上输出 CRLF）→ 运行器立刻报 17 个失败；还原后 60/60 全绿
3. 让**另一个写作者**（编程 Agent）独立使用这门语言 → 它撞到的问题都是我们视角里的盲区

**讲稿**：
> 这一页是我想重点讲的：**"测试全绿"不等于"测试有效"**。我们做了三件事来验证测试本身。第一，所有期望输出都是照着语法文档手写的，不是把解释器的输出粘回文件——如果那样做，解释器的错误会被一起固化进测试集，测试永远全绿却没有意义；手写的第一轮就抓出两处我自己算错的期望值。第二，我们发现自己原来的一个守卫是假的：运行器为了容错会把 CRLF 归一化成 LF，等于把"解释器输出 CRLF"这种回归悄悄盖住；补上真正的守卫之后，我故意把故障注入回去，运行器立刻报出 17 个失败，还原后全部恢复——**没有验证过的守卫等于没有守卫**，这招在测试学里叫变异测试。第三，我们让一个编程 Agent 只凭一份开发指南独立写程序，它撞到的输入校验坑、报回的三处指南缺口，都是我们自己不可能发现的盲区。

## 第 10 页 —— 性能测试：与 Python 对比

**页面**：数据表 + 一句话结论

| 基准 | LBX | Python | 倍数 |
|---|---|---|---|
| 递归 fib(30) | 0.844 s | 0.095 s | 8.9 倍 |
| while 累加 3000 万次 | 2.652 s | 2.433 s | 1.09 倍 |
| 冒泡排序 4000 个 | 2.146 s | 0.931 s | 2.30 倍 |

结论：**纯整数循环上几乎打平**；差距集中在函数调用（每次调用新建作用域 + 实参装箱）与数组下标（多次类型检查 + 拆箱）。

**讲稿**：
> 性能测试用三个基准，都是同一算法、同一输入，两边的输出必须完全一致，否则数据作废。最有意思的是中间那一行：纯整数循环上，我们的解释器只比 CPython 慢百分之九。这说明"语法树遍历一定比字节码慢一个数量级"并不成立——JIT 把我们的分发循环编译成了机器码，而 CPython 的字节码分发本身也有成本。真正的差距在函数调用上，差了近九倍，因为每次调用都要新建一层作用域、把实参装箱；数组下标也慢一倍多，因为每次都要做类型检查和拆箱装箱。报告里列了四条可验证的优化方向，但明确说明没有实施——因为这门作业的评分项是"性能测试"而不是"性能优化"，先把测量和归因做扎实更重要。

## 第 12 页 —— 三个真 bug 与规格演进

**页面**：三行

| bug | 现象 | 根因 | 留下的资产 |
|---|---|---|---|
| 1 | `${"内层字符串"}` 报非法字符 | 词法切字符串不知道 `${}` 内是表达式 | 回归用例 + 规格升 v1.1（`typeof` 改名） |
| 2 | `elif` 链吃掉函数的 `end` | 递归解析时内外层各消费一个 `end` | 回归用例（`05-if` 的 elif 链） |
| 3 | 输出在 Windows 上是 CRLF | `println` 用系统行分隔符 | 字节层守卫 + 变异验证；规格补 §8 说明 |

**讲稿**：
> 实现过程中抓到三个真 bug。第一个是插值里写字符串字面量，词法分析器把内层字符串的引号当成了外层字符串的结束引号；修它的时候还连带发现内置函数 `type` 和关键字 `type` 撞名，于是把内置函数改名为 `typeof` 并给规格升了版本。第二个更隐蔽：`elif` 链在递归解析时内外层各消费了一个 `end`，把函数的 `end` 抢走了，导致后面那个函数被当成嵌套定义——这个 bug 只在"if 链加 elif 加函数"三者同时出现时才暴露。第三个是行尾：`println` 在 Windows 上输出 CRLF、Linux 上输出 LF，而规格要求固定一个换行；它在控制台上肉眼看完全正常，只有在字节层才看得见。三个 bug 都留下了东西：前两个变成了黑盒用例，第三个变成了字节层守卫，并且我用注入故障的方式验证过那个守卫生效。

**页面**：

**讲稿**：
> 最后说说边界。语言明确不支持的东西都列在文档里：没有字典、没有类、没有异常处理、函数不是值——每一条都意味着解释器里少一整块机制，这是为"可实现、讲得清"付的代价。实现层有三个上限：递归深度一千层、`range` 生成一千万个元素、以及物理内存；这些是运行时资源限制，不影响语言的表达力。性能那四项优化我列了但没做，原因前面说过。另外我要主动交代两个已知盲点：一是规格和实现如果出自同一个错误假设，测试是抓不住的——唯一的解药是让第三方复核规格，比如现在；二是我们没做差分测试，那是打破这类盲点最有力的手段，代价是要另写一个独立参照实现，我评估后判断它超出作业要求。谢谢老师，请提问。

**「你的语言是图灵完备的吗？为什么？」**
> 是。判断依据是三条：能保存任意状态（变量、数组，数组还能动态增长）、能按条件分支、能无界循环。三条齐备就能模拟图灵机。语言层面没有任何循环次数或递归深度的语法限制；实现层的递归深度上限和内存上限属于运行时资源限制，任何真实语言都有。

**「黑盒测试和白盒测试有什么区别？你们为什么两种都做？」**
> 区别在于用例能依赖什么信息。白盒直接调用内部 API，断言内部状态；黑盒只通过命令行喂脚本、看标准输出和退出码。各自能测到对方测不到的东西：只有白盒能断言行列号的维护逻辑，只有黑盒能测到进程退出码和输出行尾——我们那个 CRLF 的 bug 白盒永远看不见。所以两种都做，一条命令一起跑。

**「测试是你们自己写的，怎么保证测得对？」**
> 不能保证，只能降低风险，我们做了四件事：期望值照规格手写而不是抄实现的输出；用 Python 做同算法同输入的外部对照；让另一个写作者（编程 Agent）独立使用这门语言；以及用注入故障的方式验证守卫真的有效。剩下的盲点我也说得出：规格与实现同源出错、以及没做差分测试。
